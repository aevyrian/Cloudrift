# 评论离线收藏与导出设计

日期：2026-10-30。主线：Cloudrift。原设计已完成独立复核，现按用户后续明确授权进入 1.4.0 实施；进度和验证范围见[整合实施计划](../plans/2026-10-30-history-comments-integration.md)。

在收藏库中，为用户主动选择的作品保存评论、楼中楼、评论图片和图片表情，供离线阅读并导出。普通视频下载继续按现有方式运行，只有用户点击“保存评论”才新增采集任务。

## 1 用户已确认的范围

- 原设计阶段先设计、后添加；用户后续已明确选择本轮实现并与历史功能一起推送，基本检查后先交付试用，再继续全项目审计和修复。真实采集、部署和验证状态分别记录，不把设计评审当作运行证明。
- 观看本地视频时能阅读离线评论及楼中楼，也能导出。
- 评论图片和图片表情一起保存，断开外网后可查看。
- 历史下载数量很多，评论必须是用户后续主动选择的附加功能。历史作品不自动补采，新下载也不自动采集；不遍历全库登记空评论任务。
- 保留现有浏览、视频/图集下载、媒体目录、订阅和冷却行为；不接管其他聊天正在开发的功能。

“离线”指不访问抖音或其他外网，浏览器仍需能访问本地 NAS 收藏库。导出包可搬到其他设备，但首版不新增独立播放器或离线网页应用。

## 2 技术路线

| 路线 | 适用性 | 选择 |
| --- | --- | --- |
| 复用内置 TikTokDownloader 评论采集器 | 已有主评论、回复及图片地址提取，能复用登录配置；需实测当前接口及修正结果状态 | 按上轮推荐、用户同意先设计的路线推进 |
| 浏览器助手读取网页返回的评论数据 | 依赖浏览器在线及页面加载，增加助手与服务端两端维护 | 核心路线实测失败后再评估，首版不同时建设 |
| 抖音开放平台接口 | 已查官方评论列表文档要求企业号与权限授权，不适合直接假设可读取任意收藏作品 | 首版不依赖 |

实现沿用 Python、FastAPI、SQLite、现有原生网页和容器，不新增独立服务、付费接口或消息队列。用户确定产品目标，下述交互、数据和调度细节为本设计建议。

## 3 用户怎么使用

| 场景 | 行为 |
| --- | --- |
| 日常下载与浏览 | 不采评论，不增加评论网络请求，也不为未选择的作品创建评论记录 |
| 选择一条作品 | 播放器工具栏提供“评论”入口；打开仅查询本地记录，未保存时显示“尚未保存评论”和“保存评论”按钮 |
| 旧作品缺少真实编号 | 在点击采集前显示“暂时无法识别原作品”，不提供可执行的保存按钮；已有本地存档仍可读，不声称所有旧视频都可补采 |
| 点击保存评论 | 显示将保存该作品的评论、楼中楼、图片/图片表情；一次点击入队，不要求反复确认，重复点击复用同一活动任务 |
| 已有评论 | 展示本地内容、保存时间、数量和完整性；“更新评论”由用户手动点击，不定时追更 |
| 部分完成或失败 | 已有内容仍可读；显示原因、已保存量和“继续保存”或“重试”，不显示虚假的“没有评论” |
| 正在保存 | 显示排队/采集进度，可停止；停止保留已保存内容 |
| 导出 | 对当前作品导出，含主评论及回复关系；附件包可选，导出不触发补采 |

首版只提供逐作品手动操作，不提供“全库保存”“博主全部保存”或默认开启开关，也不改 Sender 按钮和普通下载表单。视频、图集、实况使用同一评论入口。

### 评论面板

桌面端从当前播放区域右侧打开；小屏使用底部面板。沿用现有深色样式，不另起页面。顶部为“已保存 180 条评论 · 其中回复 64 条”和保存时间，数量都是本地已保存量。仅在已取得平台声明总量时另标“平台报告数量”，不据此判断采全。

正文主评论按本地首次保存顺序展示，昵称、发布时间、点赞数、正文及附件在同一条内。回复折叠在所属主评论下，显示回复对象；缺失父节点时显示“上级评论未保存”，不猜测挂到别人的评论。默认每批显示 50 条主评论，回复按需从本地分页加载。

打开面板保持当前播放或暂停状态，允许边看边读；面板打开时抑制自动切到下一条，播完留在当前作品，可手动重播。关闭后恢复正常连播规则，不强制切换、重播或改变用户后来选择的播放状态。面板内部滚动不会切换视频；手动切换作品时关闭面板并丢弃旧请求结果，避免串评论。支持键盘关闭、焦点回到入口、按钮可读标签和缺图说明。用户正文用安全文本展示，不执行 HTML。

## 4 保存什么

以真实抖音作品编号关联数据，作品编号、评论编号及回复编号均用字符串，避免大数字精度丢失。

| 对象 | 必要内容 |
| --- | --- |
| 一条评论 | 作品编号、评论编号、所属主评论编号、被回复评论/用户引用、昵称、正文、发布时间、点赞数、首次/最近保存时间 |
| 评论附件 | 所属评论、附件类型、顺序、受控来源地址、本地相对路径、摘要、保存状态和失败原因 |
| 作品采集进度 | 当前操作、主评论分页位置、未完成回复及其位置、保存数量、开始/结束时间、停止原因、分页完成与附件完成标记 |

复用 `data/library.sqlite3`，新增评论、附件和每作品采集进度三类表；具体字段名、索引及进度 JSON 结构由实现者按现有 Store 风格决定。任务只在用户选择作品后产生，不按旧库数量预分配。评论和附件按真实作品编号独立保存，不对旧库索引建立级联删除。

附件保存在 `data/comment-assets/`，使用生成的目录/文件名和内容摘要去重，不使用评论文字作为路径。成功保存后网页只读取本地地址；缺图显示占位及原因，不偷偷回退到外网。普通 Unicode 表情保留文本；图片表情和动画图片保留受支持的原始文件。首版不另外保存头像、音频评论或把内核未提供资源地址的表情臆造为图片；这类内容明确标为当前不支持，不能算完整。

所有写入均采用小事务和临时文件完成后替换。下载中断不登记为可用附件；磁盘不足停止当前任务，保留已有数据，不自动删除媒体或旧评论。现有视频媒体根和只读旧库保持不变。

## 5 更新与完整性

首次保存和手动更新均分页读取，按“作品编号＋评论编号”合并去重。重新看到的评论更新昵称、正文、点赞及最近保存时间；本轮没再看到的旧评论保留，不推断已删除。网页和导出注明“本地累计保存，非当前线上完整镜像”，每条保留自己的保存时间。

主评论和回复分别记录分页结束，回复须保留根评论及实际回复关系。不能直接沿用内核默认 `reply=false`，也不能用其共用页数预算推断所有回复已完成。页面成功解析、游标正常推进才确认进度；游标重复、结构异常、接口报错或空响应不作为正常结束。

数据状态与当前操作分开：数据可为未保存、部分保存、已遍历当次可见内容；当前操作可为等待、采集、停止、失败、中断或结束。旧数据在本轮失败时仍可读，不能被清空或标成最新成功结果。

“本次保存完成”要求本次主评论和所有发现的回复分页正常结束，并且本次发现的受支持附件全部落盘。仍只代表账号当时可见的接口结果，不保证与平台数字相等。“无可见评论”必须来自明确成功、正常结束且确实为空的结果；无数据时不能靠 `[]` 判断。存在旧存档时仍展示旧存档并注明本次未取得可见评论。

## 6 队列与资源控制

复用现有 `JobService.run_queue` 的单调度循环和核心锁，评论任务独立记录，路由只入队。媒体下载优先；无媒体任务可执行时才处理评论的一小段，完成一个请求及其落库后归还调度权。作者任务的既有 `queue_resume_at` 冷却对评论请求和附件下载同样生效，不借休息时间额外访问抖音。已有媒体下载不会因评论失败变成失败。

首版采用保守内部限制：评论接口单并发，请求间隔至少 3 秒；每次用户触发最多 200 次评论接口请求、2,000 条新保存评论（主评论＋回复）或 20 分钟实际工作时间，任一到限即停止为部分保存。每个主评论页后处理该页待取回复，再继续主评论，避免只采主评论。附件单并发、单文件最多 20 MiB、单次新写附件合计最多 200 MiB；额度耗尽或附件不支持时保留待完成信息。

这些数值是设计默认值，不是已验证的平台安全阈值。UI 在保存前简短提示“大量评论可能需分次保存”，达到限制时给出“继续保存”；普通使用不增加一页高级配置。一次排队等待和作者冷却不计入 20 分钟。

同一作品最多一个活动任务。重复点击、前后端重试不重入。第一次异常停止并给出重试入口；遇到登录验证、明确限流时暂停整个评论队列，避免转到下一作品继续请求，用户处理后手动恢复。评论错误不擅自清空 Cookie 或修改媒体任务状态。

每页内容与进度在同一事务提交；附件逐个原子落盘。2,000 条是整页完成后检查的软上限，最多超出最后一页，不截断已返回页面后却推进游标。重启把执行中标为中断，不默默无限重试。手动继续优先使用未完成位置；若游标失效，从头遍历并去重，明确提示可能重新扫描，不保证平台分页提供严格增量。继续时先补上次未完成附件及回复，额度按这次操作重新计算；附件地址过期时重新取得对应评论的地址，计入本次接口额度，取不到则保持缺失，不能无限重试旧地址。取消在当前请求超时边界内生效，之后不再发新请求。

Cookie 同步、设置更新和核心重建仍遵守同一核心锁，评论每次调度段使用当时已生效的配置。排队取消和媒体下载取消分开，现有删除下载任务仍只删其记录，不删评论或附件。

## 7 历史作品与边界

新作品使用真实作品 ID。旧库的 `legacy-*` 是路径生成的索引号，不能提交给抖音。用户选中旧作品时，只查询该作品已有编号及 `work_aliases` 中唯一可信映射；没有或存在歧义时显示“暂时无法识别原作品，不能保存评论”。首版不做全库扫描、不按标题猜测，也不新增未经验证的手工关联流程。旧库重扫或文件暂不可用不删除已存评论。

因此首版只支持有可信原作编号的旧视频补采。未知编号在旧库中占多少尚未调查；若后续用户需要补采这类作品，再单独设计“粘贴原作链接并核对关联”，本轮不把此扩展当作已经实现或已确认范围。

保存图片只接受核心返回且通过校验的 HTTPS 媒体来源；校验实际目标地址及每次跳转，拒绝本机、内网、云元数据地址等。只允许经过样本验证的抖音媒体域名，验证内容类型、文件大小和真实格式；拒绝可执行内容及 SVG 等可包含脚本的格式。附件请求不携带管理员密钥，不向外部媒体源转发抖音 Cookie。实现时建立必要允许域名列表，不写泛用下载代理。

评论读取、附件、导出和写入都沿用现有管理员鉴权；路径只从已验证数据库记录解析，不能任意读文件。API 返回和普通日志不暴露 Cookie、带访问凭证的原始 URL 或平台原始响应。存储只留本功能必要字段，不采集个人主页履历。

## 8 导出

每次只导出当前作品已保存的本地数据，无论任务是否完成。导出开始时固定数据库读取快照，避免过程中内容变化导致数量或回复关系不一致。

- JSON：带格式版本、作品编号、本地保存数量、采集时间和完整性说明；评论记录保留根评论/被回复编号及附件相对路径。评论编号均为字符串，保留原始正文。
- CSV：UTF-8 BOM，列出作品编号、评论编号、根评论/被回复编号、昵称、正文、时间、点赞、保存时间和附件路径；按标准 CSV 引号转义，公式前缀做安全转义。Excel 需要以文本方式导入编号；完整无歧义编号以 JSON 为准。
- 选“包含图片”时生成 ZIP，含 JSON、CSV、`assets/` 和简短说明；仅放本地已存在附件，缺失/不支持项目在清单注明。导出不另存视频，也不把远程带签名地址或凭据装进文件。

ZIP 流式生成或在受限临时目录生成后下载，具体方式由实现者选择；不将全部附件一次载入内存。一次导出期间固定附件引用，清理临时产物不影响正式存档。导出失败可重试，不修改采集状态。

## 9 最小改动范围

| 位置 | 预期职责 |
| --- | --- |
| `app/core.py`，必要时内置评论接口 | 接评论/回复分页，返回明确成功/结束/失败，提取必要关系及附件；改 vendor 时同步 PATCHES.md |

| `app/static/app.js`、样式及必要模板 | 评论入口、面板、楼中楼、本地图片、状态、导出及键盘操作 |

建议路由统一挂在 `/api/works/{work_id}/comments` 下：GET 本地分页及状态，POST 手动保存/更新/继续，单独取消操作，以及 export 和受鉴权附件路由。具体命名由实现者按现有 API 风格决定。首版不改 `userscripts/`、订阅周期、媒体文件布局和 Docker 挂载。

## 10 验收与后续顺序

1. 默认不采集：已有大量作品、普通新下载、打开播放器和评论面板均不会产生抖音评论请求；只有手动保存才入队，不批量建立历史任务。
2. 三类真实样本：正常文字/多级回复，图片/图片表情，多页或受限作品；先小规模验证当前核心能力、分页和字段。样本选择及真实取数放在后续实施阶段。
3. 核对本地关系：重复采集不重复，回复不串作品；重复游标、超限、验证码、网络断开、结构异常分别显示部分或失败，不冒充零评论。
4. 外网断开而局域网正常时，已保存视频、评论、楼中楼、图片/图片表情可查看；无外网图片请求，缺失附件有明确占位。
5. 停止、进程中断、磁盘写入失败或重启后，已保存内容仍在，继续不会重复；媒体成功状态、原冷却和 Cookie 更新锁保持正确。
6. JSON/CSV/ZIP 的评论数量、关系与数据库快照一致；包含长编号、换行、引号、emoji、公式前缀和部分附件样本。
7. 未登录不能读评论/附件/导出；路径穿越、外部恶意图片地址和 HTML 评论不会导致越权读写或执行。
8. 旧库无真实编号不误采，重扫不删除评论，删除下载任务不删除媒体或评论；桌面/手机滚动、连播和焦点行为不回归。

后续顺序为：小样本验证核心 → 评论存储及单队列 → 附件离线保存 → 阅读与导出 → 独立检查及真实验收 → 按后续授权部署。仅设计完成不代表任何一项运行验收已通过。

本轮独立复核已完成：补清边看边读、旧库编号限制、整页提交和过期附件重取后，复核者未发现妨碍制定实施计划的重要未决问题。上述结论只针对设计可实施性，真实接口、旧库覆盖率和运行验收均待后续验证。

## 11 交付与恢复

设计阶段只新增本文和工作记录，不改变程序或数据。实施阶段在修改前备份源文件；源码回退应保留后续用户修改，数据不随代码回退覆盖。

后续实现采用新增表/新附件目录方式，升级前备份数据库和程序。回退旧程序时保留新增评论表与附件，不删数据；须用实际旧版启动验证兼容后才声明可回退。尚未测试迁移、回退、长期运行或真实采集。
